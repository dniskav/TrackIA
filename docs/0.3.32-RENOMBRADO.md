# TrackIA 0.3.32 · de GymIA a TrackIA por dentro

La app se llamaba GymIA. Los nombres visibles ya eran TrackIA (T093); esta entrega cambia los
identificadores internos **sin perder datos**. Hecho en dos tandas el 2026-10-30.

## Qué cambió

| Capa | Antes | Ahora | Cómo se conserva lo existente |
|---|---|---|---|
| Paquete Dart y clases | `gymia`, `GymApp`, `GymRoot`, `gymTheme` | `trackia`, `TrackiaApp`, `TrackiaRoot`, `trackiaTheme` | Solo código; no afecta a los datos. |
| Claves de `flutter_secure_storage` | `gymia.*` | `trackia.*` | Migración al arrancar (`lib/data/trackia_rename.dart`). |
| Base de datos | `gymia.sqlite`, `gymia-<perfil>.sqlite` | `trackia.sqlite`, `trackia-<perfil>.sqlite` | Se copia, se verifica y el archivo antiguo se conserva. |
| Formato de copia | `gymia-backup` | `trackia-backup` | Las copias antiguas se siguen restaurando. |
| Nombre del archivo exportado | `gymia-copia-…json` | `trackia-copia-…json` | — |
| Bloques del asistente | `gymia-activity`, `-sync`… | `trackia-activity`, `-sync`… | La app lee los dos nombres (`lib/domain/block_names.dart`). |

## Migración de claves

Al arrancar, antes de leer ninguna preferencia, `migrateStorageKeys()` recorre las entradas `gymia.*`:

1. Si la clave `trackia.*` no existe: la escribe, **lee para verificar** y solo entonces borra la antigua.
2. Si existe con el mismo valor (un arranque interrumpido): borra solo la antigua.
3. Si existe con otro valor: **gana la nueva** y la antigua se queda, sin borrarse.
4. Si algo falla: la antigua queda intacta y la app sigue.

Es idempotente: volver a ejecutarla no cambia nada. Cubre las claves de ámbito de perfil y de
acompañante porque el prefijo es el mismo.

## Migración de la base de datos

`resolveDatabasePath()` devuelve la ruta que se abre:

- Si ya existe `trackia*.sqlite`, esa.
- Si solo existe `gymia*.sqlite`: pliega su registro (`wal_checkpoint`), la **copia** a un temporal,
  comprueba el tamaño y la renombra a `trackia*.sqlite`. El archivo antiguo no se toca: es la copia de
  seguridad y no vuelve a abrirse.
- Si la copia no se puede hacer (un registro con cambios pendientes, un fallo de disco), **se sigue
  usando el archivo antiguo** en esa sesión: nunca se abre una base vacía.
- Instalación nueva: `trackia.sqlite`.

El archivo `gymia*.sqlite` ocupa espacio hasta que lo borres a mano; una versión futura puede
limpiarlo cuando haya pasado tiempo suficiente.

## Lo que NO se ha cambiado, y por qué

- `applicationId` `com.gymia.app`: cambiarlo haría que Android lo tratase como otra app y no
  actualizaría la instalada.
- Los nombres de canales nativos `com.gymia.app/...`, el canal de notificación `gymia_rest` y los
  identificadores de Kotlin: Android no permite renombrar un canal ya creado.
- La clave de metadatos de Google Sheets `gymia.workout.v1`: está escrita en las hojas ya enviadas;
  cambiarla rompería el reconocimiento de los recibos.
- La cabecera de hoja `Sesión GymIA` y el `agent_name_hint` de ChatGPT (ver T093).

## Evidencia

- `test/trackia_rename_test.dart` (11): claves de perfil y de acompañante, una IA guardada que sigue
  funcionando, idempotencia, arranque interrumpido, conflicto, y la base de datos (copia idéntica,
  perfil ajeno, no pisar la nueva, instalación nueva, journal vacío y journal pendiente).
- `test/block_names_test.dart` (8) y la prueba de restauración de una copia `gymia-backup` en
  `test/sprint3_transfer_test.dart`.
- `integration_test/trackia_rename_android_test.dart` en `emulator-5554`: claves con el Keystore real y
  una base creada con el nombre antiguo, copiada y abierta con el nuevo. La primera ejecución en el
  dispositivo falló por dos razones que no aparecían en SQLite FFI (`execute` no admite un `PRAGMA` que
  devuelve filas en Android, y Android deja un `-journal` de 0 bytes) y la red de seguridad hizo
  lo previsto: siguió usando el archivo antiguo. Corregido y aprobado.
- Suite completa: 685 pruebas; `flutter analyze` sin cambios (11 avisos).

## Verificación en el teléfono con datos reales (2026-10-31)

Xiaomi 2107113SG, Android 14. Release firmado 0.3.32+35 (79,3 MB; el 0.3.31 instalado pesaba
77,7 MB), compilado con R8 activo, misma firma que la app instalada (SHA-256 `8ec5268d…2aac6`)
e instalado encima con `adb install -r` (`firstInstallTime` intacto: los datos se conservan).

- La app abre sin cerrarse, con los cuatro acompañantes, el chat de GymBro y el entrenamiento
  en curso (3/4 series) tal como estaban.
- Primer arranque: la base de datos **no se migró** («`gymia.sqlite-journal` is pending») y la
  app siguió usando el archivo antiguo sin perder nada: la red de seguridad funcionó. Causa:
  este teléfono deja el `-journal` a tamaño completo con la cabecera a cero (modo PERSIST), y la
  regla «un journal no vacío está pendiente» era demasiado estricta. Corregido: solo cuenta como
  pendiente si empieza con la cabecera mágica de SQLite (2 pruebas nuevas en
  `test/trackia_rename_test.dart`).
- Con la corrección, el arranque ya no registra el aviso y el chat y el entrenamiento siguen
  idénticos. **No pude listar los archivos** de la app (release sin `run-as`), así que la
  existencia de `trackia.sqlite` se deduce de que ya no hay mensaje de omisión, no se ha visto.
- No comprobado en el release: modelo local, avisos y Sheets (T099 sigue abierta en esos puntos).
