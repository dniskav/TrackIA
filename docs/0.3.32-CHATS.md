# 0.3.32 · Chats fuera de secure storage (US9, T084)

Fuente: `specs/004-trackia-experience/spec.md` (US9), FR-040, SC-007, `research.md` D12.

## Qué cambia

Hasta ahora el chat activo y cada chat archivado de un acompañante vivían en `flutter_secure_storage`
(Keystore en Android), con los adjuntos en base64 dentro del JSON. Ese almacén no está pensado para datos
grandes. Ahora viven en SQLite y en archivos:

| Dato | Dónde |
|---|---|
| Chat activo de un acompañante | `trackia_chats` (una fila por perfil y acompañante) |
| Chats archivados | `trackia_chat_archives` (una fila por archivo; el id guarda perfil y acompañante) |
| Bytes de los adjuntos | `trackia_media/<sha256>`, **junto a la base de datos**; el JSON guarda `{name, mime, media, size}` |

La app sigue trabajando con el mismo JSON de antes (adjuntos en línea como `{name, mime, bytes}`): el
cambio está dentro de `lib/data/chat_store.dart`. Una misma imagen enviada varias veces ocupa un solo
archivo. Las claves de API, los tokens y la configuración siguen en secure storage.

> **Desviación de D12**: la investigación decía `<applicationSupportDirectory>/trackia_media`. Se usa la
> carpeta de la propia base de datos: también es privada de la app, se mueve con ella y no depende de
> ningún plugin (con `path_provider` los tests de widget no completaban).

## Migración en dos fases (idempotentes)

1. **Copia y verificación** (al abrir un chat que aún está en la clave antigua). Se copia el chat y sus
   archivos a SQLite y a `trackia_media`, se **vuelve a leer** y se compara con el original (mensajes,
   orden y bytes de cada adjunto por su hash). Solo si coincide se marca `verified_at`. **No se borra
   ninguna clave antigua.** Si algo falla (disco lleno, adjunto que no se lee, JSON dañado) no se deja
   una copia a medias: se descarta y el chat se abre desde la clave antigua.
2. **Borrado**, en un arranque posterior. Solo se borran las claves de copias verificadas, nunca en el
   mismo arranque que hizo la copia, y se anota (`legacy_key = NULL`) para no repetirlo.

Mientras la fase 2 no ocurre, la lectura prefiere SQLite y cae a la clave antigua si no hay fila. Repetir
cualquier fase no duplica filas ni archivos.

## Archivar

Archivar escribe el archivo y el nuevo chat activo **en una sola transacción**: o cambian los dos o
ninguno. Si falla, el chat activo queda como estaba y se puede reintentar.

## Borrar un acompañante

Se borran sus filas (con el resto de sus datos de la fase 6) y sus claves antiguas. Los archivos de
adjuntos que ya no usa ningún chat se eliminan al abrir la app (`gcMedia`); un archivo usado por otro
chat o perfil se conserva.

## Recuperación

- Si la migración de un chat falla, **no se pierde nada**: la clave antigua sigue ahí y el chat se abre
  desde ella; se reintenta en el siguiente arranque.
- Un adjunto cuyo archivo falta o está dañado se detecta al leer (se comprueba su hash) y la copia no se
  da por buena.
- Los chats, archivados y adjuntos **no entran** todavía en la copia `gymia-backup` (sigue siendo v3); es el
  mismo límite que el resto de tablas nuevas de la 0.3.32.

## Límites

- La prueba de actualización sobre una instalación antigua se hizo sembrando las claves antiguas en un
  emulador con Keystore real (no instalando dos APK distintos).
- Un chat nunca abierto después de actualizar sigue en secure storage hasta que se abre.
- Los tests de widget existentes siguen usando la ruta antigua del chat (el almacén se inyecta desde la
  app); la ruta nueva se prueba en `chat_store_widget_test.dart` y en el emulador.
